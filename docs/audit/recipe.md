## 1. Architecture at a glance

- **Stack:** TypeScript strict, Expo SDK 58, React 19 with the React Compiler, React Native, react-native-web, expo-router with typed routes. Chain: `@stellar/stellar-sdk` (Soroban RPC and XDR), `@noble/curves` (ed25519 native; p256 verify in `wallet/passkey-assertion.ts`), WebCrypto Ed25519 (web), `react-native-passkeys` (create and assert). Bank approval: `react-native-plaid-link-sdk` (native Plaid Link). Third-party pages: `react-native-webview` (the redeem browser). Storage: `expo-secure-store` (native), AsyncStorage (unencrypted native, `localStorage` web), IndexedDB (web key). Also `@sentry/react-native`, `expo-updates`, `expo-local-authentication`, Apple and Google sign-in. Tests: `node --test` via `test/alias-loader.mjs`, which resolves `@/` so RN-free modules that use aliases are testable.
- **Topology:**
  - One client process per device or browser tab. Web is a static export (`app.json` `web.output: "static"`) on Cloudflare Pages with three edge functions: `/api/region`, `/api/catalog/merchants`, `/api/catalog/image`.
  - In-process guards (refresh single-flight, `InFlightPayments`, `OneTapBuy.running`, poll generations, `ReloadGate`) are per process. Cross-tab guards exist on web only via `navigator.locks` (`token-store.web.ts` `exclusive`, `ctx/payment-lock.web.ts`). Native `paymentLock` is an in-memory `memoryLock`; native `tokenStore.exclusive` is `holdCriticalReload` only, no lock. Two devices stay independent actors; only CTX serialises them.
  - A WebSocket to CTX `/ws` (`ctx/client.ts` `watchOrder`, `watchAccount`, run by `ctx/socket-watch.ts:SocketWatch`) pushes order and account events on native; `openSocket` is a no-op on web, where polling is the only channel. Events are wake signals only: state is re-fetched over REST.
  - Chain reads are hedged (`stellar/soroban.ts:Soroban.call`): the second RPC starts after `hedgeMs` (1 s) or on a transport error, and the first answer wins.
- **Environment:** `src/environment.ts` `LoopEnvironment` reads `EXPO_PUBLIC_LOOP_ENV` (`staging`|`production`; anything else throws) and fixes the CTX URL, Stellar network and client id together. `storageKey(key)` suffixes the env name so staging and production state do not mix on one device. `eas.json`: development and preview → staging, production → production.
- **Authority per entity:**
  - **CTX spend-api** (`src/ctx/client.ts`): users, sessions, merchants, gift-card orders, payments (crypto and Plaid bank), cashback ledger, payouts, wallet links, sponsoring.
  - **Stellar (Soroban):** the user's OZ smart account, token balances (SACs), DeFindex vault shares. Read by RPC simulation (`src/stellar/soroban.ts`); the app never submits transactions.
  - **Device:** refresh token, device signer key, wallet pin, sent-payment and pending-withdrawal records. Access token in memory.
  - **Cloudflare edge:** the signed-out catalog view and merchant images (cached copies of CTX data).
- **External integrations and trust:**
  - **CTX** (`loopEnvironment.ctxApiUrl`): semi-trusted. Sponsor, relayer, pricer, order book, bank-payment initiator. Builds every transaction the user signs. Design rule: never sign what CTX built without decoding and pinning it (`wallet/sponsored-call.ts`, `wallet/smart-wallet.ts`, `wallet/device-link.ts`). Trusted for prices, order state, cashback, codes; not trusted for destinations, call shape, wallet code or URLs. CTX re-derives the call at sponsor time (annex), which protects against a broken app, not a hostile CTX.
  - **CTX rates** (`ctx/rates.ts`, `https://rates.ctx.com`): the quote `BuyPrice.check` compares orders against. Same operator as the order book: independent of the endpoint, not of the party (RFC-1).
  - **Soroban RPC** (`stellar/network.ts` `rpcUrls`): two providers per network; `soroban.ts` races them after a 1 s hedge and takes the first answer, with no cross-check. Every chain-side check (wasm hash, rules, vault value, tx outcome, transfer events, latest ledger) reads through whichever answers first.
  - **Pinned contracts** (`stellar/network.ts`): account wasm hash, WebAuthn and ed25519 verifiers, payee G-address, token SACs (XLM, USDC, EURC, GBPLOOP), vaults (testnet USDC; mainnet USDC and GBPLOOP), `usdcIssuer` (read by `wallet/pay-request.ts`). `factory` and `usdc` are pinned; re-check whether anything reads them.
  - **Cloudflare edge** (`edge/catalog.ts`, `edge/region.ts`): trusted by the signed-out web and by every client for images. Unauthenticated, cached.
  - **Plaid** (via CTX): on native a CTX-returned `plaidLinkToken` opened in the Plaid Link SDK (`ctx/bank-link.ts:BankLink.present`); on web, or with no token, a CTX-returned `paymentUrl` opened in the in-app browser only when https on a plaid.com host. The SDK's `LinkSuccess` institution id and name are written back to the CTX profile (`Profile.bankUpdate` → `PUT /users/{id}`); its exit `displayMessage` is shown to the user and its `errorCode` reported.
  - **Third-party redeem pages** (`components/redeem-browser.tsx`): the CTX-supplied `redeemUrl` (any http(s) host) loads in a WebView with shared cookies and DOM storage, no navigation allow-list, and `ctx/redeem-scrape.ts:pageLinesScript` injected into every page it reaches. Untrusted: whatever the page posts back is parsed for a card number and PIN and written to CTX (INV-20).
  - **OS services:** passkey providers, biometrics, clipboard, screen capture, in-app browser, Apple/Google identity.
  - **Sentry** (`EXPO_PUBLIC_SENTRY_DSN`), **EAS Update** (signed bundles), **Friendbot** (testnet).
- **Seams where interaction bugs concentrate:**
  1. `ctx/client.ts` → `wallet/smart-wallet.ts` → `wallet/sponsored-call.ts` (or `device-link.ts`) → device signer or passkey → CTX sponsor. Every `BuiltTransaction` field crosses here.
  2. Key lifecycle: `device-key.ts`, `device-signer(.web).ts`, `passkey.ts`, `wallet-pin.ts`, `wallet-creation.ts`, CTX deploy (idempotent per credential id, ignores new keys), `rotate_device` on chain.
  3. Buy pipeline: `components/gift-card-purchase.tsx` ⇄ `ctx/one-tap-buy.ts` ⇄ `ctx/payment-sender.ts` ⇄ `ctx/payment-state.ts` ⇄ CTX order status ⇄ `/ws` events ⇄ chain transfer events. Five sources of truth for "did I pay".
  4. Session: `session/token-store(.web).ts` ⇄ `session/session-auth.ts` ⇄ CTX rotation with a 30 s reuse window; the socket authenticates once at connect.
  5. Platform splits: web holds weaker key custody, token storage and socket auth behind the same interfaces.
  6. Edge ⇄ app: `EXPO_PUBLIC_CATALOG_URL` responses and rewritten image URLs feed the same `Merchant` model as signed-in CTX responses.
  7. Two checkouts over one order model: `components/bank-checkout.tsx` (merchant page, no wallet loaded) and `components/gift-card-purchase.tsx` (pay route, wallet required) both create, approve, resume and dismiss orders through `ctx/bank-payment.ts`, `ctx/bank-link.ts` and `ctx/dismissed-orders.ts`.
  8. Vault calls: `wallet/savings.ts` ⇄ `wallet/vault-call.ts` ⇄ `wallet/savings-top-up.ts` ⇄ `wallet/pending-withdrawals.ts` share one confirm loop for deposits, withdrawals and the top-up before a pay.

## 3. Money flows

MNY is the top-weighted dimension. Every flow ends in a CTX call, a CTX-built chain transaction, or a CTX-initiated bank payment.

- **Ingress to the wallet:**
  - **External deposit** to the smart-account C-address, offered as a `web+stellar:pay` request for USDC (`wallet/pay-request.ts`). Many exchanges cannot send to a C-address.
  - **Cashback:** a CTX ledger credit first; on chain only as a threshold payout. With `cashbackDestination: savings` the payout is a gift of vault shares (annex). The app displays ledger and payout records (`ctx/account.ts`, `ctx/payout.ts`, `wallet/holdings.ts`).
  - **Friendbot** (testnet).
- **Egress:**
  - **`pay`:** SAC `transfer(wallet, M-address, amount)`, built by CTX. Pinned by `smart-wallet.ts:requirePayment`: contract = SAC for `paymentCryptoCurrency`, `transfer`, `(address, address, i128)`, payer = wallet, base of `to` = `network.payee`, `to` = `giftCard.paymentCryptoAddress`, amount = `units.parse(paymentCryptoAmount)`. The muxed destination is pinned, but to CTX's own field, not to an id derived from `paymentId` (RFC-1).
  - **Bank pay (GB):** no chain leg, and on the merchant page no wallet at all: a session alone starts it, and the user's approval at the bank is the only second factor. CTX picks the method from config (annex): `plaid-uk-eu` returns a `plaidLinkToken` (native, when the client is configured for the platform) or a hosted `paymentUrl`, both expiring after 30 min; `plaid-vrp` executes immediately against a stored payment method. The app treats `approved` from the Plaid SDK as a reason to show the card, not as proof of payment; the order status from CTX decides. The remembered bank (`bankInstitutionId`) preselects the institution on the next link token unless `chooseBank` is sent. CTX also offers EUR rails for euro-area users; `BankPayment`'s rail table holds GB/GBP only. CTX enforces per-user daily and monthly purchase limits (`ErrPurchaseLimitExceeded`); the app reads no allowance.
  - **Cash-out:** amount, sort code and account number go to CTX with the withdrawal request; one GBPLOOP payment leaves the wallet.
  - **Refund / reversal:** operator-triggered on CTX; the reversal is a CTX ledger transfer, never a chain debit (annex).
- **Internal:**
  - **`vault_withdraw`** (savings, and top-up before pay): `withdraw(i128 shares, vec<i128>[min], address)` pinned by `smart-wallet.ts:requireWithdrawal` (vault, shares, owner), floor `Holdings.floorOf(valueOf)` from RPC.
  - **`vault_deposit`** (add to savings): `deposit(vec<i128>[amount], vec<i128>[min], address wallet, bool true)` on the pinned vault with exactly one nested token `transfer(wallet, vault, amount)`, rule ids `[1, 1]`, pinned by `sponsored-call.ts:requireDeposit`. Amount from `Savings.depositAmount` (bigint, capped at the wallet balance; Max pinned at the tap). CTX sets `min = amount − 50 bps` in asset units; the app accepts any `min ≤ amount`, zero included, and pins no share floor. A sponsor answer that is lost or not a 4xx becomes `UnansweredDeposit` → `unconfirmed`; a sent call is followed by `VaultCall.confirm` (30 s, 2 s poll, `failed` once the latest ledger passes `expiryLedger` with no transaction).
  - **`rotate_device`:** passkey-signed (rule `[0]`) call on the wallet itself; pinned by `DeviceRotation.require` (contract = wallet, method, one arg = new key).
  - **Fees and reserves:** CTX relayer; the system key fee-bumps. The app does not inspect source, fee, sequence or footprint.
- **Displayed money that is not a balance:**
  - **Savings growth:** `SavingsRate.fixedBasisPoints` hard-codes 400 bps for `XLM.GBPLOOP`; `SavingsRate.projected` multiplies the on-chain vault value by simple interest since the last UTC midnight (`now % dayMs`) in `Number`, and `SavingsTicker` redraws it every 100 ms to seven sub-pence digits. The figure between daily steps is an extrapolation the chain does not hold; nothing in spend-api at `cba8f2e9` tops up the GBPLOOP vault or exposes a rate (annex), so the rate and the daily step are claims about an operation outside both repos. Other currencies show "up to 5% a year, variable" (`Savings.maxYearlyRatePercent`).
  - **Cashback rate:** `CashbackRate.ofMerchant` shows the link override, else the company default from `/me` (`CompanyCashback.effective`), else the merchant's `userDiscount`. CTX fixes the real rate per order at create time by its own formula (annex); the order's stored `userDiscountBasisPoints` is what settles. `CompanyCashback` is one instance on the client, learned in `me()` and never cleared on sign-out, so the signed-out catalog keeps showing the last user's company rate.
  - **Savings holdings:** `Holdings.savingsHoldings` shows the vault value, not the withdraw floor.
- **Order creation as money:** `OneTapBuy` creates up to two orders per tap. `OrderKeys` sends an `Idempotency-Key` **header**; CTX dedupes on an `idempotencyKey` **body field** and reads no header (annex), so the control still does nothing upstream. When the answer to `POST /gift-cards` is lost (timeout or network error, not a CTX refusal), `ctx/client.ts:placedOrder` adopts the newest unpaid order for that merchant that matches the request and was created since it was asked, allowing 5 min of clock skew (`OrderRequest.placed`); an order CTX creates after that lookup, and the one-tap re-create path, can still leave duplicate unpaid orders.
- **Value representations:** chain i128 at 7 decimals; CTX JSON decimal strings and integer basis points; app `bigint` via `stellar/units.ts`; display via `money.ts` (`Number`); quote check in basis points (`ctx/buy-price.ts`, 100 bps tolerance).
- **Who can move money:** the device key (rule 1, restricted on chain by the factory's `device_allows`); the passkey (rule 0, full control; the app uses it for `rotate_device`); the factory admin; CTX (cannot sign for the account); anyone holding the device key (a thief with biometrics; any same-origin script on web); for bank pay, anyone holding the session who can also approve at the user's bank.
- **Who can write a card's code:** the owner's session, once, while the card is fulfilled with no number and no PIN (`PUT /gift-cards/{id}/number`, annex); in the app that write is driven by whatever page the redeem WebView is showing.

## 4. Trust boundaries & threat model

| Adversary | Capabilities | Goal |
|---|---|---|
| Unauthenticated internet user | `/login`, `/verify-email` (CTX: 20 min expiry, 5-attempt lock); craft `loop://` and universal links into any route; hit the edge functions with any query | Account takeover via CTX; abuse the image proxy or poison the catalog cache |
| Authenticated customer | Any customer-role CTX call, including ones the app never calls (wallet link CRUD, `send`, recovery start, payment methods) | Reach another user's data, pay once and claim twice, duplicate orders; start CTX recovery and, after dormancy plus the timelock, replace both signers of a wallet the session reaches (Loop #94) |
| Compromised or buggy CTX | Every JSON field: `BuiltTransaction`, wallet links, order amount/currency/address, rates, codes, `redeemUrl`, `barcodeUrl`, `paymentUrl`, merchant text and images, socket events, error bodies | A signature for a CTX-chosen amount, destination or call; a hostile URL in the in-app browser; a wallet the user does not control |
| Lying Soroban RPC (either provider) | Every simulation, ledger entry, event and tx status; with hedging, answering first is enough to be the one believed | Pass `verify()` for a wrong account; zero the withdraw floor; fake "paid", "deposited" or "rotated" |
| Hostile or compromised redeem page (the supplier's site, anything it redirects or links to, an ad or script on it) | Any DOM text in the redeem WebView; the injected script's `postMessage` channel (no origin check); cookies and storage shared with the system store | Plant a wrong card number and PIN on the user's CTX card (fill-once, so the real code can no longer be saved); phish inside an app-branded modal; read the real code off the page |
| Plaid SDK and bank-side data | `LinkSuccess` institution id and name, `LinkExit` error code and display message, link events | Put attacker text in front of the user or into the CTX profile; steer the next payment's preselected bank |
| Holder of the local Android signing key | An APK that Android verifies for `loopfinance.io` app links and passkey credential sharing (`get_login_creds`) | Receive the app's links; use the user's passkey from a look-alike build |
| Same-origin script on web | `localStorage` (refresh token, pin, records), the IndexedDB CryptoKey, the live session | Steal the session; sign with no gesture; forge the wallet pin |
| Device adversary | App UI, backups, screenshots, app switcher, clipboard | Read codes; use the session |
| Cloudflare / edge config | Catalog responses, image bytes, response headers, CSP | Serve a lookalike catalog or image; drop CSP |
| Supply chain | JS bundle dependencies, install scripts, GitHub Actions | Swap destinations before signing |
| Insider with repo / CI access, or a developer machine with deploy credentials | `network.ts` pins, `environment.ts`, release workflow, OTA signing key; `npm run deploy:web` from any checkout; the local Android keystore | Repoint payee or verifier; ship a signed bundle; publish an unreviewed web build |

- **Assets:** wallet funds; the user's bank account (reachable through bank pay); gift-card codes and bearer URLs (`redeemUrl`/`barcodeUrl` carry 10-year view tokens that cannot be revoked); the device key; the passkey; the CTX session (90-day rotating refresh token); bank details typed into cash-out; PII (email, legal name, country, bank institution, purchases); the OTA signing key (CI secret); the local Android keystore; Cloudflare deploy credentials.
- **Boundaries:**
  1. CTX `BuiltTransaction` → `SponsoredCall.verify` + `require*` → device or passkey signature.
  2. CTX wallet link → `WalletPin.choose` → `WalletRules.check` (RPC) → wallet treated as the user's.
  3. CTX order, merchant and payment fields → UI, `Image`, `ExternalLink`, `openBrowserAsync`.
  4. Route params and universal links → CTX paths (`giftCard(id)` and `merchant(slug)` encode; wallet ids from CTX do not).
  5. JWT payload → path segment (`client.ts:userIdFrom`, no validation).
  6. Edge: internet query → `CatalogQuery` whitelist → CTX; image `src` → S3 prefix check → fetch.
  7. `/ws` socket: native sends auth headers; web opens no socket. CTX accepts `?token=&clientId=` on the upgrade (annex), which would put the access token in a URL if the app used it. CSP `connect-src` lists only `https:` origins (check whether target browsers let them match `wss:`).
  8. Build/CI: `environment.ts` constants, release workflow ref gate, OTA code signing; the local web deploy and local Android signing sit outside that gate.
  9. Third-party page → app: redeem WebView `onMessage` → `readPageLines` → `parseCardDetails` → `ctx.saveGiftCardCode`. The message's origin is not checked; the parse heuristics are the only filter.
  10. Plaid SDK → app: link token in, institution and exit text out (`BankLink.approved`, `BankLink.left`) → CTX profile, toast, Sentry message.
  11. Bank return and pay routes: `/orders/[id]` and `/shop/pay/[slug]` take raw route params into a redirect and a merchant lookup.
- **Sensitive data:**
  - Refresh token: native SecureStore via `InstallScopedToken` (wiped when the AsyncStorage install marker is missing, so a reinstall drops it); web `localStorage` `ctx.refreshToken` (not env-scoped).
  - Device secret: native SecureStore `device.signer.<userId>`, `requireAuthentication: true`; web non-extractable CryptoKey in IndexedDB.
  - Wallet pin: native SecureStore, web AsyncStorage (`wallet-pin.ts` `pinStorage`).
  - Codes: memory, copied with expiry (iOS) or flagged sensitive (Android), capture blocked while details are mounted (native); also visible inside the redeem WebView, whose cookies and DOM storage persist in the shared store across sign-out.
  - Cash-out bank details: component state, then sent to CTX; the response carries the sort code and the account number's last four digits.
  - Local records in AsyncStorage: `loop.dismissedOrders` (order ids; not user- or env-scoped), `loop.purchaseTermsAccepted.<userId>`, `payments.sent.<paymentId>`, `savings.withdrawal.<address>.<currency>`, `appLock.enabled.<env>`, `market.country`, `welcome.seen`, favourites per user.
  - Sentry messages name order ids and Plaid error codes (`bank-checkout.tsx`, `gift-card-purchase.tsx`); the scrubber's patterns do not match UUIDs.

## 5. Invariants (with enforcement tiers)

Tiers: **chain** > **runtime** > **test** > **convention**. **CTX** marks a check in spend-api, outside this repo's control. Tier = weakest writer. "Test: none" means no test asserts the failure case. All cites @ee1fd44. INV-19 to INV-23 were derived in the `ee1fd44` refresh; their tiers went through a recipe-skeptic (§11).

### INV-1 — Never sign a transaction that was not decoded and pinned locally
- **Statement:** every signature is over a locally recomputed OZ digest (`sponsored-call.ts:authDigest`) for one `invokeHostFunction` op with one address-credential auth entry for this wallet, auth call = op call, expiry = `built.expiryLedger` within `(latest, latest + 120]`, and `contextRuleIds` equal to the rule ids the intent expects (`[1]` device, `[0]` passkey, `[1,1]` device deposit). Sub-invocations are allowed only when the intent carries one rule id per level and the intent's `require*` pin checks every level (`requireDeposit`: the vault call plus its one nested token transfer).
- **Enforced by:** runtime `SponsoredCall.verify(built, wallet, ruleIds, latestLedger)`; device path through `smart-wallet.ts` (`pay`, `deposit`, `signWithdrawal`), passkey path through `device-link.ts:DeviceLink.add`. CTX re-checks the call at sponsor time. Test: `sponsored-call.test.ts` asserts the refusals (one rule covering nested calls, two rules without a nested call, nested-in-nested, digest mismatch, wrong rule ids) and compares `authDigest` to a digest "computed independently" for a transfer; check that the vector comes from outside the app's own formula.
- **Keeping it:** any new intent adds a `require*` pin between `verify` and signing; nothing else may call `deviceSigner.sign` or a passkey assertion for a CTX-built payload.

### INV-2 — A pay signature moves only the quoted amount of the quoted token to this order's address
- **Statement:** `contract == SAC(paymentCryptoCurrency) ∧ method == transfer ∧ from == wallet ∧ base(to) == network.payee ∧ to == paymentCryptoAddress ∧ amount == units.parse(paymentCryptoAmount)`, and the order matches the request (`OrderRequest.matches`: merchant, currency, fiat amount) and an independent USD quote within 100 bps (`BuyPrice.check`).
- **Enforced by:** runtime `requirePayment`, `OrderRequest.matches` (`ctx/client.ts:orderGiftCard`), `BuyPrice.check` (`ctx/one-tap-buy.ts`). Chain: rule-1 `device_allows`. Tests: `order-request.test.ts`, `buy-price.test.ts`, `one-tap-buy.test.ts`; for `requirePayment` itself, check `smart-wallet.test.ts`.
- **Gaps:** destination and quote are CTX data (RFC-1); the rates feed is CTX's. Muxed id not derived from `paymentId`.

### INV-3 — A withdraw signature burns only the requested shares into this wallet above a floor
- **Enforced by:** runtime `requireWithdrawal` (vault, shares, owner), floor `Holdings.floorOf(valueOf)`; `signWithdrawal` under `holdCriticalReload`. Tests: `savings.test.ts`, `savings-top-up.test.ts`, `holdings.test.ts`.
- **Gaps:** floor source is whichever RPC answers first; GBPLOOP vault on mainnet only (`network.ts` `vaults`); CTX needs the chain-qualified currency and does not normalise a bare `USDC` (annex). The savings tab withdraws the user's full share balance.

### INV-4 — The wallet in use runs pinned code, holds exactly the user's two signers, and is the one this user pinned
- **Statement:** `wasmHash == pinned ∧ rules == 2 ∧ rule0 = one permanent External WebAuthn signer (= pinned passkey key) ∧ rule1 = one ed25519 signer`, and the address is the user's pinned address; `thisDevice` is `linked` only when rule 1 holds this device's key.
- **Enforced by:** runtime `WalletRules.check`, `WalletPin` (`choose`, `admits`, `pinCreatedHere`, `pinConfirmed`, `requireCurrentUser`), `SmartWallet.load`/`create`. Pin in SecureStore on native. Tests: `wallet-rules.test.ts`, `wallet-pin.test.ts`, `smart-wallet.test.ts`.
- **Gaps:** trust-on-first-use: unpinned, `choose` takes the first usable link. Every passkey confirmation runs through `WalletIdentity.prove` (assertion against on-chain rule 0, address derived by the factory from the asserting credential id) and a pin naming another wallet or passkey is discarded on load (#241), so the gap is the first link only. Web pin is in `localStorage`. Rule policies not checked. CTX recovery (a customer permission) replaces both signers after dormancy plus a timelock; the app never reads pending recovery and has no cancel (Loop #94); the dormancy and timelock values are unverified against the contract source. `WalletPin.passkeyForSetup` treats any failed assertion, a cancelled prompt included, as a lost passkey and creates a new one.

### INV-5 — Money arithmetic is exact
- **Enforced by:** runtime `units.parse` (max 7 decimals), bigint compares in `require*` and `Merchant.cashbackEstimate`, basis-point math in `BuyPrice`. Tests: `money.test.ts`, `merchant.test.ts`, `buy-price.test.ts`, `amount-input.test.ts`.
- **Gaps:** `money.ts` display via `Number`; `OrderRequest.matches` compares a truncated fiat amount (check the truncation cannot accept a different order).

### INV-6 — Each order is paid at most once, and a tap creates only the orders it means to
- **Enforced by:** CTX: one in-flight sponsored tx per payment (`ErrPaymentAlreadySubmitted`), `pay` only on `pending`. Chain: auth nonce. Runtime: `InFlightPayments`, `paymentLock` (`memoryLock` native, `navigator.locks` web), `SentPayments`, `canPay`, `OneTapBuy.running`, `maxOrders = 2`. Tests: `payment-sender.test.ts`, `sent-payments.test.ts`, `in-flight-payments.test.ts`, `payment-state.test.ts`, `one-tap-buy.test.ts`, `memory-lock.test.ts`.
- **Gaps:** CTX dedupes on an `idempotencyKey` body field the app does not send and ignores the header it does send, so order creation is not idempotent upstream (RFC-13, RFC-14). `OrderKeys` now keys on `chooseBank` too, so a "different bank" retry is a second order by design. Cancelling is local (`DismissedOrders`): the unpaid order lives on at CTX, and every bank order with no payment started is hidden from resume whether or not it was dismissed. `hidden` requires `cancellable` (unpaid, no payment started), so an order resumes again once CTX shows money on it; between the user's approval and that update only `settle`'s single re-fetch or the wallet list shows it. The lost-answer recovery in `ctx/client.ts:placedOrder` closes the user-retry path only when CTX created the order before the lookup (a recovered order must be on the asked rail; a pending idempotency key is renewed after 30 minutes, #238). `transferMatches(value, null)` is fail-open; both callers pin the order's amount and muxed id through `PaymentSearch.orderTransfer`, so a null expectation reaches it only for an order with no crypto amount or address. Cross-device double pay rests on CTX alone.

### INV-7 — A session belongs to one user and sign-out ends it
- **Enforced by:** runtime: per-user device key `device.signer.<userId>` (regex-validated id; the legacy shared-key fallback is gone), per-user pin keys, `WalletPin.requireCurrentUser`, session generation counter and `useSessionOwner`; `sign-in.tsx` signs out a different email first; `SessionAuth.storeTokens` refuses a refresh that returns another user's access token (or one whose owner cannot be read), ends the generation, notifies `onSessionEnd` and leaves that refresh token unrotated until the next sign-in or sign-out (#242); `SocketWatch` closes its socket on session end. Tests: `device-key.test.ts`, `wallet-pin.test.ts`, `session-owner.test.ts`, `session-auth.test.ts`, `socket-watch.test.ts`.
- **Gaps:** sign-out (`ctx/client.ts:signOut`) keeps the device key and the pin; `SentPayments` and pending-withdrawal records are keyed by payment id / address, not user; favourites cleared only on a deletion request; check the web device-signer for any surviving shared-key read.

### INV-8 — Refresh tokens rotate without losing the session
- **Enforced by:** runtime `SessionAuth` single-flight and generations; a 401 rotates only when CTX names `ErrTokenInvalid` (`CtxError.refusesToken`, #242); web `navigator.locks`; native no lock (one process). CTX: rotation with a 30 s reuse window. Tests: `session-auth.test.ts`, `session-tokens.test.ts`.
- **Gaps:** `sendRefreshToken` retries once on a non-`CtxError` with the same token (reuse inside CTX's window). `sessionRequest` replays once, with the refreshed token, a request CTX refused with `ErrTokenInvalid`, `POST /gift-cards` included; CTX rejected the first attempt before creating anything. `SocketWatch` retries with backoff to a 30 s ceiling and takes one replacement token per run of failed handshakes, a rotation it cannot tell from a network failure.

### INV-9 — Gift-card codes reach only their owner and do not leak from the device
- **Enforced by:** CTX ownership on `GET /gift-cards/:id`; socket payloads carry no secrets. Runtime: capture block while details are mounted, switcher blur, clipboard expiry, barcode shown only on reveal, `redeemUrl` opened only if `externalUrl.isWeb`.
- **Gaps:** bearer view tokens in URLs (10-year, not revocable); `isWeb` allows any http(s) host; web has no capture protection; no biometric re-prompt before codes show; the redeem WebView shows the code on a third-party page and feeds its text to the app (INV-20); whether `useBlockScreenCapture` covers the redeem `Modal` is unverified.

### INV-10 — Pinned chain constants match the selected network, and CTX and network are paired
- **Enforced by:** runtime pairing: `LoopEnvironment` fixes CTX URL + network per env and throws on anything else. Pins vs chain: convention (nothing checks the pins against the live network in CI). Whether CTX's payee equals `network.payee` is CTX config.

### INV-11 — CTX requests carry only the caller's identity and well-formed paths
- **Enforced by:** CTX IDOR guard. Runtime: `giftCard(id)` and `merchant(slug)` encode. Not enforced: wallet ids in `/wallets/${walletId}/stellar/*` (CTX-supplied); `userIdFrom` unvalidated.

### INV-12 — Profile updates send only whitelisted values
- **Enforced by:** runtime `Profile.nextUpdate` against CTX company lists; `UserUpdate` = country | stableCurrency | cashbackDestination | legalName | bankInstitutionId + bankInstitutionName. CTX refuses `stableCurrency` changes once set and shape-checks the institution id (annex). Test: `profile.test.ts`.
- **Gaps:** the bank institution pair comes from Plaid SDK output (`Profile.bankUpdate`), not from a list the app holds; the name is free text up to CTX's 80-rune cap.

### INV-13 — App lock covers the app whenever it is on and stale
- **Enforced by:** runtime `AppLock` (`session/app-lock.ts`): locks on load failure, after 5 min background or a clock jump; unlocks on success **or** `not_enrolled`/`passcode_not_set`. Web: no-op. Test: `app-lock.test.ts` covers the state model only; `components/app-lock.tsx` has no test. A UI cover, not a key gate: bank checkout needs no device key, so on a device with the lock off, or one where the lock unlocks on `not_enrolled`, the session alone reaches Pay.
- **Gaps:** after a successful check the cover stays opaque for `unlockHoldMs` with `pointerEvents: none`, so taps land on content the user cannot see. The redeem browser is an RN `Modal` in its own native window: the lock cover sits beneath it and `closesBrowser` dismisses only the `expo-web-browser` sheet, so a locked app leaves an open redeem page on top.

### INV-14 — Error reports carry no secrets or PII
- **Enforced by:** runtime `SentryScrubber` with an `allowKeys` whitelist, `sendDefaultPii: false`, `ctxReportMessage` status + name only, `UnexpectedResponse` reports from `ctx-response.ts`. Tests: `sentry-scrubber.test.ts`, `ctx-report.test.ts`, `signing-report.test.ts`.

### INV-15 — A JS bundle swap never interrupts a pay and never runs code the release did not sign
- **Enforced by:** runtime: `expo-updates` code signing (`app.json` `updates.codeSigningCertificate`, rsa-v1_5-sha256) and `ReloadGate`/`holdCriticalReload` around pays, sign-in and withdrawals. CI: `release.yml` publishes production only from `v*` tags and checks the certificate and project id. Tier: runtime (was convention).

### INV-16 (new) — A device is linked only by a passkey-signed rotation the app pinned
- **Statement:** `rotate_device` is signed by the passkey (rule `[0]`), the call is the wallet's own `rotate_device(newDevicePublicKey)` with the key this device just created, and the assertion is a valid `webauthn.get` over the digest.
- **Enforced by:** runtime `DeviceLink.add` → `SponsoredCall.verify(…, [0])` → `DeviceRotation.require` → `PasskeyAssertion.requireSigned` (type, challenge, p256 verify). Chain: rule-0 WebAuthn verifier. Tests: `device-link.test.ts`, `device-rotation.test.ts`, `passkey-assertion.test.ts`.
- **Gaps:** `requireSigned` checks neither `origin` nor `rpIdHash`; the chain verifier decides. CTX stores no device key, so nothing off chain records the rotation. CTX recovery replaces rule 0 and rule 1 with no passkey signature (Loop #94).

### INV-17 (new) — Untrusted URLs open only on allowed schemes and hosts
- **Enforced by:** runtime `externalUrl.isWeb` for `redeemUrl`; edge `CatalogImage` S3 prefix + width whitelist; CSP from `src/ops/content-security-policy.ts` injected at build (`scripts/content-security-policy.ts`). Bank `paymentUrl` opens only as https on a plaid.com host, and an off-host link is reported once per order (`components/gift-card-purchase.tsx`, #238, #240). `CatalogImage` accepts one plain bucket key, keys the cache by canonical origin plus path and serves only image content types with `nosniff` and a sandboxed CSP (#239). **Not enforced:** merchant `website`; the redeem WebView's host and its in-page navigation (no `originWhitelist`, no `onShouldStartLoadWithRequest`); `barcodeUrl` and logo hosts on native; the `/orders/[id]` param before the redirect.

### INV-18 (new) — Signed-out catalog requests reach CTX only with whitelisted parameters
- **Enforced by:** runtime `edge/catalog.ts:CatalogQuery` (keys `enabled, order, country, name, ids, category, page, perPage, slug`, ≤ 512 chars each). Tests: `edge/*.test.ts`. CTX treats several of these as regexes (annex), so a whitelisted key still carries a regex.

### INV-19 — A deposit signature moves only the requested amount of the wallet's token into the pinned vault for this wallet
- **Statement:** `contract == vault(currency) ∧ method == deposit ∧ desired == [amount] ∧ min.length == 1 ∧ min[0] ≤ amount ∧ owner == wallet ∧ invest == true`, with exactly one nested call `token.transfer(wallet, vault, amount)` and rule ids `[1, 1]`.
- **Enforced by:** runtime `SponsoredCall.verify(…, [1, 1], …)` then `requireDeposit` (`smart-wallet.ts:signAndSponsorDeposit`, the only writer), under `holdCriticalReload`. Chain: rule-1 `device_allows`. Test: `sponsored-call.test.ts` asserts each refusal (other contract or method, other amount, min above amount, other owner, `invest` false, zero or two transfers, three rules); `savings.test.ts`, `vault-call.test.ts` cover amount parsing and the confirm loop.
- **Gaps:** no floor on shares minted, so a manipulated vault price can mint few shares for the full amount (`min` bounds asset amounts, not shares, and the app accepts zero or negative: the test asserts zero is accepted); the vault and token are the app's pins, the share price is the chain's. `UnansweredDeposit` leaves the user with "may still be confirming" and no stored record to reconcile: only the top-up before a pay keeps `PendingWithdrawals`; deposits and savings-tab withdrawals keep none. The savings-tab withdraw (`app/savings/index.tsx`) calls `wallet.withdraw` → `SavingsTopUp.send` with no `VaultCall.settle`, checks only `result.error` and then reports success, so a `failed` status with no error, or a transaction that never lands, reads as moved (RFC-17).

### INV-20 — A card's code is written only from the card's own redeem page, once, and matches what the page shows
- **Statement:** `PUT /gift-cards/{id}/number` is sent only while the card has no number and no PIN, at most once per mount, with values `parseCardDetails` read from the redeem page.
- **Enforced by:** CTX: owner-only, fill-once (`AwaitsCode`), no length or charset check (annex). Runtime: `awaitingCode` and the `saving` ref in `redeem-browser.tsx`; `numberValue` (10–30 alphanumerics, ≥ 8 digits) and `pinValue` (3–10) in `redeem-scrape.ts`. Test: `redeem-scrape.test.ts` covers the parser, including prose that mentions a code; nothing tests the component or the message channel.
- **Tier: convention for "from the card's own page".** Nothing binds the message to the `redeemUrl` origin: any page the WebView navigates to runs the injected script, and any script on any such page can call `ReactNativeWebView.postMessage` with lines of its choosing. Because the write is fill-once, a wrong value is permanent for the customer. The script also collects `input` and `textarea` values (password, hidden and button types excepted), so a number the user types under a "Card number" label on the page, a payment card included, passes `numberValue` and is sent to CTX as the gift-card number. A failed save leaves the `saving` ref set, so nothing more is tried until the browser is reopened.

### INV-21 — A bank order is shown as bought only when CTX says it is paid
- **Enforced by:** runtime: `stageOf` and `BankPayment.resumed` read `order.status`; `settle` re-fetches before deciding; the order detail page polls and listens until a settled status and shows "Waiting for your bank to confirm the payment" while unpaid. CTX: payment status from Plaid webhooks (annex). Test: `bank-payment.test.ts`, `bank-link.test.ts`, `dismissed-orders.test.ts`; `bank-checkout.tsx` has no test.
- **Gaps:** in `bank-checkout.tsx` only, `approved` from the SDK pushes straight to `/wallet/{id}` and fires the success haptic with no status check, and the browser path shows the card as soon as the browser closes; the pay route returns quietly on `approved` and re-fetches after the browser (`approveInLink`, `approveAtBank`). The pay route hands any `plaidLinkToken` to `BankLink.present` with no web guard, where `bank-checkout.tsx` has one. Approval links are checked for host only on the `paymentUrl` path; a `plaidLinkToken` is opaque and handed to the SDK as is. The approval window is 30 min (`paymentUrlExpiration`); `stageOf` re-evaluates every 30 s.

### INV-22 — A displayed rate or balance never exceeds what the user can actually realise
- **Statement:** the savings figure equals the vault value, the yearly rate shown is the rate the product pays, and the cashback shown before buying equals what the order will credit.
- **Enforced by:** convention. `SavingsRate.fixedBasisPoints` is a constant; `projected` adds accrual the chain has not paid; `CompanyCashback` mirrors a CTX rule from one `/me` field while CTX prices by a formula with a margin cap (annex). Tests (`savings.test.ts`, `merchant.test.ts`) check the arithmetic against itself, not against CTX or the chain.
- **Gaps:** no top-up job or rate endpoint exists in spend-api at `cba8f2e9`; a missed daily step leaves the ticker ahead of the withdrawable value until the next reload; `Number` math on a 7-decimal bigint; the risk note calls the rate variable while the headline states a fixed 4%.

### INV-23 — What reaches users was built from a reviewed ref and signed by a key only the release process holds
- **Enforced by:** CI: `release.yml` ref gate (production from `v*` tags), signed OTA, certificate presence check. Convention: `npm run deploy:web` (any checkout, any branch, production env), local Android signing, and the second fingerprint in `assetlinks.json`.
- **Gaps:** the web app, which holds the same session and the web device key, ships with no ref gate and no CI build; `release.yml` checks the certificate is non-empty, not that it pairs with the private key; `release.yml` requires `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` while `environment.ts` hard-codes `googleIosClientId: ''`; CI has no export or build step, so a web build break is found at deploy time.

### Weakest links (ranked) @ee1fd44
0. **INV-20 code write from an unauthenticated page channel**, user-typed input included, permanent because CTX fills once. **INV-19 savings-tab withdraw reported as done with no chain confirm.** **Web signing refused outright by a key mismatch (L48).** **INV-23 web deploy and local Android key outside the release gate.** **INV-22 the 4% rate and the live ticker rest on an operation neither repo contains.** **INV-19 no share floor on deposit.**
1. **INV-6 order creation not idempotent upstream:** the app sends an `Idempotency-Key` header; CTX dedupes on a body field. A lost answer is recovered from the unpaid orders placed since the request (`ctx/client.ts:placedOrder`, `OrderRequest.placed`), but an order CTX creates after that lookup, and one-tap re-create on price expiry, still duplicate orders. Session replay is not a path: `sessionRequest` replays only a request CTX refused with 401, so nothing was created.
2. **INV-4 / INV-16 CTX recovery replaces both signers** with no passkey signature and no app-side view (Loop #94). ## 7. Tech-specific traps

1. **OZ smart-account digest is not the Soroban payload.** Sorted ScMap `{account, context_rule_ids, signature_payload}`; a library bump can change it.
2. **`TransactionBuilder.fromXDR` returns `FeeBumpTransaction` for fee-bump envelopes.**
3. **`scValToNative` on a muxed address returns `M…`.** Strip and compare the id deliberately (`muxedIdOf`).
4. **Simulation reads are unauthenticated;** with two RPCs, failover takes whichever answers.
5. **`expo-secure-store` with `requireAuthentication`** is invalidated on biometric change; Keychain survives uninstall (the install marker handles this for the token only).
6. **WebCrypto Ed25519** non-extractable keys stay usable by any same-origin code.
7. **`react-native-passkeys` returns SPKI DER;** assertions return DER signatures that must be low-S compact for the verifier.
8. **WebAuthn assertions bind origin and rpId in `clientDataJSON` and `authenticatorData`;** checking only type and challenge leaves those to the verifier.
9. **Passkey RP id:** `PasskeySite.forHost` maps web hosts to `loopfinance.io` except localhost; staging hosts must be associated.
10. **expo-router params are decoded strings or arrays;** the generic is a type assertion.
11. **`EXPO_PUBLIC_*` are inlined at build time and public.**
12. **`Number` in display** loses precision beyond 2^53; **`BigInt(n)`** throws on non-integers.
13. **React Compiler** memoizes automatically.
14. **CTX refresh tokens rotate on every call; reuse inside 30 s revokes the new chain.**
15. **CTX signature expiry is 60 ledgers (~5 min).**
16. **AsyncStorage is unencrypted** on native and is `localStorage` on web.
17. **`navigator.locks`** exists only on web; native `memoryLock` is per process.
18. **OIDC ID tokens without a nonce** are replayable for their lifetime.
19. **`expo-updates` `reloadAsync`** drops in-memory state; code signing protects only builds that embed the certificate.
20. **`expo-local-authentication` error codes** differ per platform.
21. **`rpc.Server.getEvents`** covers only the retention window.
22. **The browser `WebSocket` takes no headers.** RN accepts a third options argument with headers; the browser ignores it, so auth must travel in the URL, a subprotocol, a first message or a cookie.
23. **CSP and `wss:`:** CSP Level 3 lets an `https:` source match `wss:` on the same host; older engines need an explicit `wss:` source.
24. **Cloudflare cache keys** include the full URL by default; a whitelist that drops unknown keys upstream must also keep them out of the cache key, or junk queries fragment or share entries.
25. **CTX regex filters:** `slug`, `name`, `ids`, `country` on `GET /merchants` are regexes; a bare value is a partial match.
26. **Headers CTX does not implement** (`Idempotency-Key`) give no protection, however carefully the client generates them; CTX's own control is the `idempotencyKey` body field.
27. **`react-native-webview` `injectedJavaScript` runs on every top-level page load,** not only the first URL, and `window.ReactNativeWebView.postMessage` is callable by any script on any of those pages. `onMessage` carries the page URL in `nativeEvent.url`; nothing checks it unless the app does.
28. **WebView defaults:** `originWhitelist` defaults to http and https, `sharedCookiesEnabled` joins the system cookie store, `domStorageEnabled` persists per site, and none of it is cleared on sign-out.
29. **Plaid Link `onSuccess` means the user finished the flow,** not that money moved; payment state arrives at CTX by webhook. `onExit` text and error codes are Plaid- and bank-supplied.
30. **Hedged requests take the first answer.** Racing two RPCs improves latency and makes the faster provider the trusted one for that read; a `NOT_FOUND` from a lagging node can race a real result.
31. **`Date.now() % dayMs` steps at UTC midnight,** not at the moment an off-chain job runs; a projection anchored to it drifts from the chain by the job's offset and by any missed run.
32. **`pointerEvents: 'none'` on an opaque view** lets touches reach what is underneath while the user sees the cover.
33. **`assetlinks.json` trusts every listed fingerprint equally** for app links and for `get_login_creds` (passkey and credential sharing); a development key listed there is a production key.
34. **A Reanimated `exiting` view stays in the tree** for the length of the animation with its last props.

## 8. Recurring failure classes

- **RFC-1 — Upstream data compared to upstream data.** Destination = `paymentCryptoAddress`; quote = CTX rates; wallet address = CTX link. For each `require*`, ask where the expected value came from.
- **RFC-2 — Fail-open guards.** Checks that skip when an optional argument is missing (`transferMatches(…, null)`, unpinned passkey key).
- **RFC-3 — Platform split weaker on one side.** Diff each `.ts`/`.web.ts` pair; include the socket (headers vs none) and the token store (env-scoped vs not).
- **RFC-4 — Secrets in visible text or URLs.** Codes; bearer URLs; bank details in mock forms.
- **RFC-5 — Per-user state outliving the user.** Records keyed by payment id or address.
- **RFC-6 — Strings as protocol.** CTX error names and message text.
- **RFC-7 — Docs as claims.** `PRODUCT.md`, marketing pages, commit messages.
- **RFC-8 — Unbounded waits.** Bounded by `Deadline` and expiry polls; check new loops.
- **RFC-9 — Unencoded identifiers in paths.** Wallet ids.
- **RFC-10 — Compatibility fallbacks that widen authority.** TOFU pin, `navigator.locks` absent, image proxy fallback fetch.
- **RFC-11 — Local records treated as truth.** Sent payments, pending withdrawals, wallet pin, install marker.
- **RFC-12 — Sign now, act later.** `SignedPayment.sponsor`, passkey rotation then sponsor, `ReloadGate`.
- **RFC-13 — Retries that are not idempotent upstream.** `/refresh-token`, `POST /gift-cards`, one-tap re-create, sponsor.
- **RFC-14 — Client controls an upstream does not honour.** Headers, fields or arguments the app sends that the receiver ignores (`Idempotency-Key` header vs CTX's body field, socket headers in a browser). Verify each control on the receiving side, and re-verify when the upstream changes: CTX gained idempotency and a browser socket handshake and the app uses neither.
- **RFC-15 — Local-only state standing in for an upstream action.** "Cancel" that only hides an order (`DismissedOrders`), terms acceptance kept per device, a remembered bank. Ask what the upstream still believes.
- **RFC-16 — Displayed money computed apart from its source.** The savings ticker, the fixed rate, the company cashback default. For each figure, name the authority and check the screen cannot run ahead of it.
- **RFC-17 — Success shown on a signal that is not the authority.** Plaid `approved` and browser closed in `bank-checkout.tsx`; the savings-tab withdraw toasting on the sponsor answer. The haptic and the navigation should follow the order or chain state.
- **RFC-18 — One flow implemented twice.** Bank create/approve/settle in `bank-checkout.tsx` and `gift-card-purchase.tsx`; a fix to one is a regression waiting in the other. Diff the pair.
- **RFC-19 — Untrusted page or SDK output crossing into a trusted write.** Redeem page text → CTX card code; Plaid institution → CTX profile; exit message → toast.
- **RFC-20 — Keys that differ between writer and reader.** `SmartWallet.confirmed` is filled with `confirmedKey()` and read with `this.address` at sign time (lead L48). Look for the same shape in storage keys and lock names.
- **RFC-21 — Release paths beside the gated one.** A manual deploy or a local signing key that reaches users without the checks the workflow applies.
